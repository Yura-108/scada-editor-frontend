# Контракт тегов: правки для scada-gateway и фронта

Дата: 05.08.2026. Ветка бэкенда: `microservice`.
Соседний проект: `Z:\Project Java\scada-gateway` (`SCADA_GATEWAY_PATH` в `.env`).

Документ — задание на правки в **двух чужих зонах**: шлюз и фронт. Всё, что делает
runtime, описано в части C — чтобы обе стороны видели границу ответственности.

Контекст: лёгкий `tools/kafka-sim` заменён реальным шлюзом, он опрашивает PLC-симулятор
по OPC UA и Modbus и публикует все 2471 канал BN1_MCA1. Телеметрия уже работает.
Не работает запись в ПЛК и не показывается потеря связи — об этом ниже.

---

## 0. Три принципа, из которых выведено всё остальное

**Идентичность тега — это путь канала, и ничего кроме.**
`Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST` — он же Kafka-key телеметрии, он же
`ComponentProperty.tag_id` в редакторе, он же адрес в команде. Никаких числовых
идентификаторов на проводе: у шлюза их два (`channel_id` и внутренний PK таблицы
`tags`), они не равны друг другу, и наружу не публикуется тот, который нужен для
записи. Любое числовое поле в сообщении становится ложным кандидатом в
идентификаторы — именно на этом мы уже потеряли время.

**Протокол — деталь реализации шлюза.** Наружу он не торчит ни в телеметрии, ни в
команде. Runtime не знает и не должен знать, читается канал по OPC UA или по Modbus:
он адресует путь, а маршрутизацию делает шлюз по своей конфигурации тега. Формат
сообщений для обоих протоколов **побайтово одинаковый**.

**Значение и достоверность — разные оси.** «Клапан закрыт» и «состояние клапана
неизвестно» — разные состояния, и смешивать их в одном поле нельзя. Сейчас они
смешаны, и это порождает худший из возможных исходов на мнемосхеме (см. A3).

# Часть A. Правки в scada-gateway

Шесть правок. A1–A3 согласованы, A4 блокирует запись целиком, A5–A6 нужны для
честной обратной связи оператору.

## A1. Тело телеметрии — три поля вместо тринадцати

**Файл:** `SCADA-gateway/src/main/java/com/scada/gateway/kafka/producer/TelemetryProducer.java`
(метод `sendTelemetry`, строки 38–95; такой же разбор нужен `sendFieldTelemetry`, строки 100–135)

**Сейчас** в топик уходит `TelemetryMessage` из 13 полей:

```json
{ "messageId": "0f2c9a1e-…", "type": "TELEMETRY", "tagId": 385,
  "tagName": "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST",
  "value": true, "numericValue": 1.0, "stringValue": "true",
  "unit": null, "quality": "GOOD", "timestamp": "2026-08-05T09:14:22.183Z",
  "controllerId": 1, "controllerName": null,
  "metadata": { "device": "LINE1V0", "field": "ST", "deviceType": "V" } }
```

**Нужно:**

```
key:   "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST"      ← без изменений, tag.getName()
value: { "value": true, "quality": "GOOD", "timestamp": "2026-08-05T09:14:22.183Z" }
```

| Поле | Тип | Правило |
|---|---|---|
| `value` | `bool` / `number` / `string` / `null` | **Типизированный скаляр, не строка.** `null` — только при `quality: "BAD"` |
| `quality` | `"GOOD"` \| `"BAD"` | `GOOD` только если значение реально прочитано с контроллера |
| `timestamp` | ISO-8601 UTC | Момент снятия значения, а не отправки — см. A2 |

Поле `quality` оставлено строкой намеренно: если позже понадобится развести
`UNCERTAIN` (у OPC UA это отдельное состояние `StatusCode`), контракт расширяется
без ломки — фронт и runtime трактуют всё, кроме `"GOOD"`, как недостоверное.

**Что удаляется и почему это безопасно:**

| Поле | Почему не нужно |
|---|---|
| `tagId` | `channel_id`, для записи не годится. **Главная причина правки** — убрать ложный идентификатор |
| `tagName` | Дублирует Kafka-key. Runtime читает key: проверка подписки идёт до разбора JSON. **Касается только телеметрии** — в команде (A4) одноимённое поле остаётся и становится основным адресом тега |
| `numericValue`, `stringValue` | Runtime приводит тип из `value` сам |
| `unit` | `null` у всех 2471 тега в `application.yaml` |
| `messageId`, `type` | Дедупликации нет, топик односортный |
| `controllerId` | Не используется |
| `controllerName` | Шлюз его никогда не заполняет (LAZY-прокси, `getName()` кинул бы `LazyInitializationException`) |
| `metadata` | Объектная модель прибора. **Единственная реальная потеря.** Нужна была монитору для сборки прибора из каналов; в редакторе объект собирается по дереву проекта, а не по метаданным телеметрии |

Побочный эффект: при 2471 канале и `pollingRate: 2000` это ~1240 сообщений/с.
Сообщение ужимается с ~400 до ~90 байт — с ~490 до ~110 КБ/с.

> Если у топика когда-нибудь появится второй потребитель, которому нужны `metadata`
> или `controllerId`, — это повод завести отдельный топик, а не возвращать поля.
> На 05.08.2026 потребитель один (подтверждено).

## A2. `timestamp` — момент снятия значения, а не момент отправки

**Файл:** тот же, строка 58: `message.setTimestamp(Instant.now());`

`Instant.now()` в момент формирования сообщения — это фактически время приёма,
только на пару миллисекунд раньше нашего собственного. Никакой новой информации
такое поле не несёт, и держать его в ужатом теле смысла нет.

**Нужно:**

- **OPC UA** — `dataValue.getSourceTime()`: время, когда значение зафиксировал сервер.
  `DataValue` уже есть в цикле опроса (`OpcUaClientServiceDB.java:369`, рядом
  берётся `getStatusCode()`), передать его в продюсер — вопрос сигнатуры.
  Если `sourceTime` пуст — фолбэк на `getServerTime()`, затем на `Instant.now()`.
- **Modbus** — источника времени в протоколе нет. Ставить момент **завершения
  чтения регистра**, а не момент отправки в Kafka.

Разницу между «настоящий sourceTime» и «фолбэк» наружу выносить не надо: runtime
трактует поле одинаково.

## A3. Слать сообщение и при `value == null`

**Файл:** `SCADA-gateway/src/main/java/com/scada/gateway/opcua/OpcUaClientServiceDB.java`, строка 578

```java
if (value != null) {
    telemetryProducer.sendTelemetry(tag, value, quality);
} else {
    log.debug("⚠️ {} = NULL (quality: {})", tag.getName(), quality);   // ← сообщения нет
}
```

**Проблема.** Самый частый BAD — обрыв связи — до потребителя не доходит вообще:
при исключении чтения вызывается `processTagValue(tag, null, "BAD")` (строки 383, 462),
и отправка пропускается. До нас доезжает только редкий случай «прочитали, но статус
плохой».

Следствие на экране оператора: **тег замирает на последнем значении и выглядит
живым.** Мнемосхема показывает состояние часовой давности как текущее.

**Нужно:** отправлять всегда, независимо от качества:

```json
{ "value": null, "quality": "BAD", "timestamp": "2026-08-05T09:14:22.183Z" }
```

**Про объём.** Дополнительного трафика это не создаёт: шлюз и в норме шлёт каждый
тег каждый цикл опроса, без дельта-фильтра. BAD-кадры идут ровно с той же частотой,
что и GOOD, — то есть при обрыве нагрузка не растёт, а остаётся прежней.

**Важно:** это единственная из правок, которая **без доработки на нашей стороне
делает хуже**. `null`, доехавший до JS-скрипта как значение тега, — falsy, и биндинг
вида `setState(tag ? 'Открыт' : 'Закрыт')` уверенно нарисует клапан **закрытым** при
потере связи. Замерший тег плохо, тег с уверенно неверным состоянием — хуже.
Поэтому A3 внедряется **только вместе с** частями B и C (см. C4).

## A4. Принимать команду по имени тега — без этого запись не работает вообще

**Файл:** `SCADA-gateway/src/main/java/com/scada/gateway/kafka/CommandConsumer.java`

**Это блокирующая правка.** A1–A3 — направление «шлюз → мы», записи они не касаются.

**Сейчас** строка 46 отбрасывает команду без числового `tagId`, строка 54 зовёт
`writeTag(cmd.getTagId(), …)`, а `writeTag` резолвит тег через `tagCache.get(tagId)`,
где ключ — **внутренний PK** таблицы `tags` (`OpcUaClientServiceDB.java:672`, кэш
заполняется на строке 242 как `tagCache.put(tag.getId(), tag)`).

Этот PK нигде не публикуется: телеметрия несёт `channel_id`, REST-эндпоинта со
списком тегов нет (`MonitoringController` — только `/api/health`, `/api/events*`;
`StatusController` — `/api/status`). Единственный источник — БД шлюза.

**Почему нельзя подставить `channel_id` из телеметрии.** `channel_id` и PK — разные
нумерации: PK выдаёт Postgres при первой синхронизации YAML (`ConfigurationService.
syncDatabaseFromYaml`, строка 61, вставка идёт в порядке YAML), `channel_id` приходит
из базы каналов. Для клапана `V_ST_1.LINE1V0.ST` это `id=1` и `channel_id=385`.
`tagCache.get(385)` находит **существующий чужой тег** — 385-й по порядку YAML,
это `Барановичи-1.BN1_MCA1.V_M_2.V2.M`, FLOAT-измерение другого прибора на
подключённом контроллере. Не ошибка, а запись не туда. На реальном железе — запись
в чужой прибор.

**Нужно:** резолвить тег по `tagName` — полю тела `CommandMessage`, которое runtime
**уже присылает в каждой команде**, а шлюз сейчас использует только для лога
(`CommandConsumer.java:52`). То есть правка не добавляет поле в протокол, а
перестаёт игнорировать имеющееся.

> **Не путать с A1.** Там из тела `TelemetryMessage` удаляется поле `tagName` —
> это другой класс, другой топик и обратное направление. `CommandMessage` правка A1
> не затрагивает; поле `tagName` в команде остаётся и становится основным адресом.
>
> Путь канала в двух направлениях живёт в разных местах намеренно:
>
> | | Телеметрия (шлюз → runtime) | Команда (runtime → шлюз) |
> |---|---|---|
> | Адрес тега | Kafka-key | поле `tagName` в теле |
> | Роль ключа | адрес | только порядок команд по тегу |
>
> В телеметрии ~1240 сообщений/с, и подписка проверяется **до** разбора JSON — тело
> неподписанного тега не парсится вообще, поэтому адрес обязан быть в ключе. Команд
> единицы в минуту, тело разбирается всегда, и адрес в нём устойчивее: команда без
> ключа всё равно доедет и останется адресуемой.

Имя самодостаточно: оно стабильно и не зависит от истории БД, в отличие от
суррогатного PK.

Числовой `tagId` мы не шлём и слать не будем. Обратную совместимость с Monitor Srv
(если он ещё где-то живёт) можно сохранить, приняв **любой** из двух: есть `tagId` —
резолвим по нему, иначе по `tagName`.

Реализационно рядом уже есть готовый образец: `ConfigurationService` держит
второй индекс `tagByNodeIdCache` с публичным `getTagByNodeId()` (строки 179, 204).
Индекс по имени — то же самое.

**Заодно стоит поправить `isOpcUaTag`** (`OpcUaClientServiceDB.java:488`): он
возвращает `true` при любом непустом `node_id`, а колонка `NOT NULL` — и Modbus-тег
с `node_id = "modbus:40001"` проходит проверку «это OPC UA», падая дальше с ложным
диагнозом «Контроллер не подключён». Протокол надо проверять первым.

## A5. Различимые статусы в `scada-command-results`

**Файл:** `SCADA-gateway/.../opcua/OpcUaClientServiceDB.java`, `CommandOutcome` (строка 743)

**Сейчас** исход — пара `status` (`APPLIED` / `REJECTED` / `FAILED`) плюс
свободный русский текст в `message`. Отличить «тега нет» от «узел только на чтение»
и от «контроллер отвалился» программно нельзя — только парсингом текста.

Оператору нужно видеть разницу: «канал не существует» — это ошибка конфигурации
проекта, а «нет связи» — эксплуатационная ситуация.

**Нужен фиксированный перечень:**

| `status` | Когда |
|---|---|
| `APPLIED` | Записано, контроллер подтвердил |
| `REJECTED_UNKNOWN_TAG` | Тег с таким именем не найден |
| `REJECTED_NOT_WRITABLE` | Узел только на чтение (`BadNotWritable`) |
| `REJECTED_TYPE_MISMATCH` | Значение не приводится к типу тега |
| `REJECTED_PROTOCOL_UNSUPPORTED` | Запись для этого протокола не реализована (см. A6) |
| `FAILED_NO_CONNECTION` | Контроллер не подключён |
| `FAILED_WRITE` | Прочая ошибка записи |

`message` остаётся как есть — человекочитаемая расшифровка для логов.

**Тело результата** (топик `scada-command-results`, key = путь канала):

```json
{ "commandId": "3f2b8c14-9d05-4e77-8a1b-6c2e0f4d7b93",
  "tagName": "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST",
  "status": "APPLIED", "success": true,
  "message": "Записано значение true", "appliedValue": true,
  "timestamp": "2026-08-05T09:14:25.204Z" }
```

`tagName` обязателен (по нему коррелируем, если потеряется `commandId`), числовой
`tagId` не нужен.

## A6. Запись в Modbus

Сейчас записи в Modbus в шлюзе нет как кода. Это **1877 каналов из 2471** — по ним
нельзя применить ни одну уставку, а `ModbusClientService` умеет только чтение.

**Нужно одно из двух:**

1. **Реализовать запись** (предпочтительно) — тогда контракт команды остаётся
   единым и runtime по-прежнему ничего не знает о протоколах.
2. **Если пока не реализуется** — отдавать `REJECTED_PROTOCOL_UNSUPPORTED` (A5)
   сразу, не пытаясь искать OPC UA-клиент. Тогда оператор увидит честную причину,
   а не «контроллер не подключён».

Чего делать **не надо**: выносить протокол в телеметрию, чтобы runtime фильтровал
записываемые каналы на своей стороне. Это ломает принцип «протокол — деталь шлюза»
и возвращает в сообщение поле, которое мы только что оттуда убрали.

## A7. Идемпотентность по `commandId` (желательно, не блокирует)

`commandId` мы генерируем на каждую команду и шлём всегда. Шлюз сейчас использует
его только как эхо в результате.

Двойной клик по кнопке = две записи. Для тумблера клапана безобидно, для операции
вида «увеличить уставку» — нет. Окна последних N применённых `commandId` (N ~ 1000,
TTL ~ минута) достаточно.

# Часть B. Правки на фронте

## B1. `tags[]` получает поле `quality`

**Контракт сейчас** (`docs/FRONTEND_RUNTIME_INTEGRATION.md:143`):

```json
{ "type": "UPDATE",
  "tags": [ { "tagId": "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST",
              "value": "false", "ts": 1784696916495 } ],
  "properties": [ … ] }
```

**Станет:**

```json
{ "type": "UPDATE",
  "tags": [ { "tagId": "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST",
              "value": "false", "ts": 1784696916495, "quality": "GOOD" } ],
  "properties": [ … ] }
```

Правило разбора: `quality` отсутствует или `"GOOD"` — значение достоверно;
**любое другое** значение — недостоверно. Не проверять на равенство `"BAD"`:
контракт расширяемый, позже может появиться `UNCERTAIN`.

`properties[]` не меняется. Свойство — результат работы скрипта, а не сырое
значение канала; качество относится к тегу.

## B2. Рендер «нет данных»

При `quality != "GOOD"` компонент, привязанный к этому тегу, должен показывать
**«нет данных»**, а не значение.

Важная деталь: **`value` при этом остаётся заполненным** — там последнее известное
достоверное значение (или `null`, если достоверного ещё не было ни разу). Так
сделано намеренно: оператору полезно видеть «было открыто, связь потеряна 40 с
назад», а не пустоту. Как это показать — решает фронт; варианты: приглушить
компонент, наложить штриховку/значок, показать значение серым с меткой времени.

Чего делать **нельзя**: трактовать `value` при `quality != "GOOD"` как текущее
состояние. Это ровно та ошибка, ради устранения которой заводится поле.

## B3. `ts` сменил смысл

Было — момент приёма сообщения бэкендом (`System.currentTimeMillis()`).
Станет — **момент снятия значения с контроллера** (A2).

Следствия:
- `ts` **перестаёт быть монотонным**: у разных тегов в одном кадре времена
  разойдутся, а при переподключении к контроллеру возможен скачок назад.
- Если где-то есть сортировка по `ts` или вычисление «свежести» — проверить.
- Зато появляется осмысленный возраст значения: `now - ts` — это реальная
  задержка от ПЛК до экрана, её можно показывать при `quality: "BAD"`.

## B4. Холодный старт перестаёт выглядеть поломкой

Шлюз обходит 2471 канал последовательно, полный круг ~90 секунд, а consumer
читает с конца топика (`auto.offset.reset=latest`). До первого значения тег
существует, но значения не имеет.

Сейчас это выглядит как пустой экран без объяснения. После правок такой тег
приходит как `value: null, quality: "BAD"` и штатно рисуется как «нет данных» —
отдельной обработки холодного старта не требуется.

# Часть C. Что делает runtime (моя зона, для сведения)

Чтобы обе стороны видели границу: ниже — работа в `scada-editor-backend`,
задания она не содержит.

**C1. Парсер телеметрии.** `TagValueRouter.extractValue` читает из конверта
`value`, `quality`, `timestamp`. Совместимость со старым 13-польным форматом
сохраняется: в обоих есть `value`, отсутствующий `quality` трактуется как `GOOD`,
отсутствующий `timestamp` — как время приёма. Порядок внедрения A1–A3 относительно
нашего релиза значения не имеет.

**C2. Состояние тега.** `TagRuntimeState` начинает хранить раздельно последнее
**достоверное** значение, текущее качество и метку времени. Сейчас там только
`lastValue`. Нужно, чтобы сессия, подключившаяся во время обрыва, получила
последнее известное значение с честным `quality: "BAD"`, а не пустоту.

**C3. WS-кадр.** `TagUpdate` получает поле `quality` — это то, что описано в B1.

**C4. Скрипты не видят `null` от плохого качества.** При `quality != "GOOD"`
`onChange`-биндинги **не запускаются**: значение тега не изменилось, оно стало
неизвестным. Компонент остаётся в последнем состоянии, а «нет данных» рисует
фронт по `quality`. Это ответ на риск из A3 — и причина, по которой A3 нельзя
внедрять раньше этой правки.

**C5. Consumer `scada-command-results`.** Корреляция по `commandId`, отчёт
`POST /api/runtime/recipes/apply` начинает показывать реальный исход вместо ack
брокера. Требует A4 и A5.

**C6. Настоящий `onChange`.** Сейчас биндинг срабатывает на **каждое** сообщение,
а не на изменение значения: сравнения с предыдущим в `TagValueRouter` нет нигде.
С `kafka-sim` на трёх тегах это было незаметно, с реальным шлюзом каждый
подписанный тег дёргает GraalVM раз в 2 секунды впустую.

Правка отложена до C5 сознательно: сейчас именно это «ложное» срабатывание
служит единственным подтверждением того, что команда доехала. Если сделать
настоящий `onChange` раньше, чем появится честное подтверждение, запись значения,
**равного текущему**, перестанет давать какую-либо реакцию на экране.

# Часть D. Открытые вопросы

**D1. Отклик кнопки — 2 секунды.** Полный цикл: клик → команда → запись в узел →
следующий опрос (`pollingRate: 2000`) → телеметрия → `onChange` → перерисовка.
Оператор жмёт и до двух секунд не видит реакции. Варианты: оптимистичная отрисовка
с откатом по таймауту (фронт), снижение `pollingRate` для писабельных тегов (шлюз),
либо принять как есть. Решения нет.

**D2. Запись в канал с `quality: "BAD"`.** Сейчас команда уйдёт в тег, связь с
которым потеряна. Блокировать на нашей стороне, предупреждать на фронте или
пропускать — не решено.

**D3. Узлы сцены в симуляторе только на чтение.** `plc-simulator/config/replay_config.yaml`:
теги 385 и 389 заведены `access: RO, generator: replay`, OPC UA-сервер выставляет
узел писабельным по этому флагу (`core/plc.py:199`). Любая запись отобьётся как
`BadNotWritable` независимо от A4. Тестовые данные, правится в рабочем порядке
вместе с A4; `generator: replay` для этих узлов надо снять, иначе архивное значение
будет подставляться в тег каждый цикл.
