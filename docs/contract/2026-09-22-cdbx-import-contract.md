# Контракт: импорт базы каналов из `.cdbx` — что добавить на фронте

Дата: 22.09.2026, дополнен 23.09.2026 (вложения исходников ptusa — раздел 1.1, коммит `a62cb8d`).
Бэкенд — `main`, коммит `44c7729`. Проверено на стенде напрямую на `channel` (8082) полным
`BN1 MCA1 NEW.cdbx`; через gateway (8080) с токеном — ещё нет (`scada-90op`). Вложения на стенде
не проверялись, только юнит-тестами и разбором настоящих файлов.

Спека — `docs/superpowers/specs/2026-09-22-cdbx-import-object-channels-design.md`.

## Коротко

На странице «База каналов» (`/channels`) нужны три действия: **импорт `.cdbx`** в новый проект,
**удаление импортированного проекта** и **выгрузка тегов для шлюза**. Всё остальное фронт уже умеет:
импортированный проект — обычные узлы и параметры, дерево и панель параметров показывают их без правок.

Новая база строится **по объектам**: `Барановичи-1.BN1_MCA2.LINE1.V0.ST` вместо
`…V_ST_1.LINE1V0.ST`. Для редактора схем и монитора это просто другой путь тега — привязки работают
как раньше. Старая база `BN1_MCA1` не меняется.

## Что сделать

1. **Кнопка «Импорт .cdbx»** — диалог: файл, площадка, проект **и два необязательных файла
   исходников ПЛК** (раздел 1.1) → `POST /api/channel/import/cdbx`, после ответа показать отчёт и
   обновить дерево.
2. **Действие «Удалить импортированный проект»** на узле проекта → `DELETE /api/channel/import/{site}/{project}`
   с подтверждением.
3. **Действие «Выгрузить для шлюза»** на узле проекта → `GET /api/channel/export/gateway`, показать
   текст с кнопкой «Копировать» или отдать файлом.
4. **Три прокси-маршрута** в `src/app/api/device/…` по образцу соседних (`protectedRoute`,
   `Authorization: Bearer`, `backendErrorResponse`).

## 1. Импорт

```
POST /api/channel/import/cdbx
Content-Type: multipart/form-data
  file     — файл .cdbx (до 20 МБ; у BN1 — 2,4 МБ)
  site     — площадка, например «Барановичи-1»; без точки
  project  — имя нового проекта, например «BN1_MCA2»; без точки
  io       — необязательно: main.io.lua из исходников проекта ptusa
  objects  — необязательно: main.objects.lua оттуда же
```

Площадку и проект вводит пользователь — из файла они **не** берутся. Площадку удобно выбирать из
`GET /api/channel/node/sites` с возможностью ввести новую; проект — свободное поле.

**Ответ `200`:**

```json
{
  "root": "Барановичи-1.BN1_MCA2",
  "nodes": 3025,
  "channels": 2647,
  "merged": ["OBJECT1.RT_PAR_F[119]", "…"],
  "guessedType": ["SYSTEM.UP_TIME", "LINE1WATCHDOG1.P_T_GEN", "…"],
  "skipped": [],
  "unmapped": ["SYSTEM", "OBJECT4", "LINE1WATCHDOG1"]
}
```

Показать отчёт после импорта:

| Поле | Как показать |
|---|---|
| `root`, `channels` | «Создан проект Барановичи-1.BN1_MCA2: 2647 каналов» |
| `merged` | «55 каналов объединены — одна переменная ПЛК была в двух группах» (список — под спойлер) |
| `guessedType` | «У 121 канала тип данных угадан (FLOAT) — проверьте параметр «Тип данных»» (список — под спойлер) |
| `skipped` | если не пуст — «Пропущены: …», имена без поля |
| `unmapped` | если не пуст — «6 объектов не нашлось в исходниках ПЛК и разложены по общему правилу» (список — под спойлер). Всегда пусто, если файлы ПЛК не приложили |

## 1.1. Два необязательных файла исходников ПЛК (с 23.09.2026)

**Зачем.** В `.cdbx` имя объекта слито в одну строку (`CIPV101`, `MCA4LINE1DI1`), а
технологические объекты безлики (`OBJECT1`…`OBJECT17`). Без подсказки бэкенд делит имена по
общему правилу и угадывает не всегда; техобъекты при этом получают выдуманные имена линий.
Исходники проекта ptusa дают точное деление и человеческие имена.

| Поле формы | Файл | Что даёт |
|---|---|---|
| `io` | `main.io.lua` | точное деление имени прибора (`CIPV101` → `CIP.V101`) и описания приборов для каналов, у которых описания в `.cdbx` нет |
| `objects` | `main.objects.lua` | настоящий техобъект: `OBJECT6` → `TANK1.MIX_NODE` вместо выдуманного `LINE6.OBJECT` |

**Оба файла необязательны и независимы** — можно приложить один, оба или ни одного. Без них
импорт работает как раньше, ничего не ломается.

**В диалоге импорта** — отдельный блок, свёрнутый по умолчанию: «Исходники проекта ПЛК
(необязательно, но дерево получится точнее)». Два поля файла с именами-подсказками
`main.io.lua` и `main.objects.lua`; расширение не проверять, бэкенд разберёт что дали и молча
пропустит непохожее. Файлы небольшие — 100–400 КБ.

Поясняющий текст рядом: «Эти файлы лежат в проекте ПЛК рядом с `main.plua`. Без них приборы
раскладываются по общему правилу, а объекты получают имена вида `LINE1.OBJECT`».

**Отправка** — те же `FormData` и тот же прокси: поля добавляются в форму, если пользователь их
выбрал. Прокси-маршрут править не нужно, он пересылает форму целиком.

**После импорта проверьте `unmapped`.** Туда попадают объекты, которых не нашлось в приложенных
файлах и которые разложены общим правилом. Это не ошибка: `SYSTEM` и `RECMAN` приборами не
являются никогда. Но длинный список — признак, что файлы от **другой ревизии проекта**: так у
базы мойки `main.objects.lua` описывает 3 объекта, а в её `.cdbx` их 6, и `OBJECT4…6` уезжают в
общее правило. Стоит показать это заметно, а не прятать под спойлер, если список длиннее
двух-трёх имён.

**Ошибки** (тело — `{ timestamp, status, message }`, `message` показать как есть):

| Код | Когда |
|---|---|
| `409` | проект `site.project` уже есть — импорт только создаёт новую базу |
| `400` | не `.cdbx`, битый XML, в файле нет каналов, пустые или с точкой `site`/`project` |

Импорт идёт одной транзакцией: при ошибке в базе ничего не появляется. На BN1 он занимает ~2 с —
достаточно спиннера на кнопке.

**Прокси.** Файл отдать дальше как `FormData`, **не** выставляя `Content-Type` руками — boundary
проставит `fetch`:

```ts
// src/app/api/device/import/route.ts
export const POST = protectedRoute(async (req: NextRequest, {token}) => {
  const form = await req.formData();
  const response = await fetch(`${BACKEND_URL}/api/channel/import/cdbx`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${token}` },
    body: form,
  });
  if (!response.ok) return backendErrorResponse(response);
  return NextResponse.json(await response.json());
});
```

## 2. Удаление импортированного проекта

```
DELETE /api/channel/import/{site}/{project}
```

- `204` — проект со всем поддеревом удалён, площадка осталась.
- `409` — проект создан не импортом (у узла проекта нет параметра «Источник импорта»). Так этим
  действием не удалить `BN1_MCA1` или базу, собранную руками. Показать `message`.
- `404` — такого проекта нет.

Показывать действие только на узле проекта с параметром «Источник импорта» (он есть в ответе
`fullHierarchy` среди параметров узла). Подтверждение обязательно: **отмены нет**, через «Отменить»
(`/api/channel/undo`) импорт и удаление не откатываются — они не пишутся в журнал команд. Текст
подтверждения: «Удалить проект BN1_MCA2 целиком? Схемы, привязанные к его тегам, потеряют связь».

`site` и `project` в пути кодировать `encodeURIComponent` — площадка кириллическая.

## 3. Выгрузка для шлюза

```
GET /api/channel/export/gateway?root=Барановичи-1.BN1_MCA2&controllerId=ptusa-mca2&endpoint=pac://127.0.0.1:10000
```

Ответ `200 text/plain` — готовый блок для `controllers.yaml` шлюза:

```yaml
    - id: ptusa-mca2
      name: "Барановичи-1.BN1_MCA2"
      endpoint: "pac://127.0.0.1:10000"
      enabled: true
      tags:
        - {name: "Барановичи-1.BN1_MCA2.LINE1.V0.ST", nodeId: "pac:9476", channelId: 9476, deviceName: "LINE1V0", fieldName: "ST", deviceType: "V", protocol: pac, dataType: INT32, pollingRate: 2000, enabled: true, writable: true}
```

- `controllerId` и `endpoint` спросить у пользователя; подставить по умолчанию `ptusa-<проект в
  нижнем регистре>` и `pac://127.0.0.1:10000`.
- `404` — под `root` нет каналов с параметром «Имя в ПЛК» (например, старая `BN1_MCA1`).
- Рядом с текстом — подсказка: «Вставьте блок в controllers.yaml шлюза и пересоберите его —
  без этого теги нового проекта не будут приходить».

Прокси отдаёт текст как есть: `new NextResponse(await response.text(), { headers: { 'Content-Type': 'text/plain; charset=utf-8' } })`.

## Что уже работает без правок

- **Дерево и панель параметров.** Импортированный проект — обычные узлы: `LINE1` → `V0` → `ST`.
  С приложенными исходниками ПЛК рядом с приборами появляется узел технологического объекта,
  названный его типом: `LINE1.MAIN_CIP_MODULE`, `TANK1.TANK`, `TANK1.MIX_NODE`, `GR1.LINE_IN`.
  Это обычный узел, отдельной обработки не требует.
  У узлов каналов появились параметры «Имя в ПЛК» (`LINE1V0.ST`), «Тип данных» (`INT32`/`FLOAT`/`STRING`),
  у узла проекта — «Источник импорта». Их типы приходят в `GET /api/channel/param/description`
  (id на стенде 20–22, но искать по имени). Показывать и редактировать как остальные параметры.
- **Выбор тега в редакторе схем** — пути длиннее и по объектам, формат тот же (строка через точку).
