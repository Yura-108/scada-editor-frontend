# Runtime: проект вместо сессии. Дизайн этапа 1

Дата: 16.09.2026. Статус: согласован, к реализации.

## Зачем

Сейчас всё, что делает `runtime`, привязано к сессии мониторинга, то есть к открытому
экрану оператора. Уход со страницы рвёт WebSocket, `RuntimeSessionReaper` закрывает
сессию, и вместе с ней останавливается работа, которая к экрану отношения не имеет:
процедура рецепта перестаёт переходить по шагам, серверные скрипты `on_change` больше
не исполняются.

Требование: **мойка, запущенная оператором, идёт до конца независимо от того, смотрит
на неё кто-нибудь или нет.** Оператор заходит в монитор, запускает процедуру, закрывает
браузер — на заводе процедура продолжается. Монитор становится наблюдателем с правом
действия, а не владельцем работы.

Обнаружено при прогоне рецепта «Танк сырого молока №2 — Дезинфекция» 16.09.2026 (см.
`docs/RECIPE_CIP_HOTWATER.md`). Два прогона из двух сорвались по этой причине.

## Что ломается сегодня — по фактам

1. **Процедура зависает молча.** `ProcedureExecutionService` держит исполнения в
   `Map<ExecutionKey(sessionId, recipeId), ...>`. Сессию убили — `condition_script`
   получает из `readProjectTag` только `null`, условие никогда не становится истинным.
   При этом `GET /status` бодро отвечает `200` с растущим `elapsedMs`: снаружи процедура
   выглядит живой.
2. **Возврат в монитор создаёт новую сессию** (`runtimeConnection.ts:235` делает `DELETE`
   при уходе), и процедура, привязанная к старому `sessionId`, становится недоступной:
   `confirm`/`jump`/`status` отвечают `400 No active procedure`.
3. **Повторный `start` глушит идущую мойку.** Запуск в новой сессии применяет действия
   шага 0, а у «Дезинфекции» шаг 0 — это «закрыть всё»: 14 клапанов в 0, насос, возврат,
   `P_ZAD_FLOW` и `P_ZAD_PODOGR` в 0. Именно так 16.09.2026 остановился прогон на
   20-минутной выдержке: насос встал, температура возврата ушла с 86 до 9 °C, условие
   `TE2 >= 85` после 1200 с не выполнилось.
4. **Скрипты размножаются по сессиям.** `TagValueRouter` на изменение тега делает
   `for (String sessionId : state.sessionIds) dispatchToSession(...)`, и `on_change`
   запускается внутри этого цикла. При двух открытых мониторах каждый серверный скрипт
   исполняется дважды, и запись в ПЛК внутри него уходит дважды.
5. **Состояние свойств у каждого своё.** `RuntimeSession.propertyValues` инициализируется
   из начальных значений дерева. Оператор A нажал кнопку, `ACTION`-скрипт записал свойство —
   оператор B этого не увидит никогда. Копии расходятся и не сходятся обратно.
6. **Значения тегов живут, пока есть сессии.** `TagValueRouter.registerSession` создаёт
   записи в `tagStates`, `unregisterSession` их убирает. Без сессий значений нет вообще.

## Границы

**В этапе 1:** перенос владения с сессии на проект, персистентность процедур, проектное
состояние свойств, сессия как наблюдатель, один экземпляр `runtime`.

**Не в этапе 1** (фиксируется как целевая картина, заводится в beads):

- несколько экземпляров `runtime` с распределением драйверов;
- топики телеметрии и команд на драйвер (требует правок в `scada-gateway`);
- маршрутизация монитора к экземпляру-владельцу в `gateway`;
- журнал моек (история завершённых процедур);
- снимок `propertyValues` в компактный топик для переживания перезапуска.

## Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Что включает проект в `runtime` | Явный флаг «в эксплуатации» у проекта в `editor` | Единственный вариант, дающий понятную кнопку ввода в эксплуатацию. Признак «есть задачи», как в `automation`, для `runtime` не работает: дерево есть у любого проекта |
| Состояние свойств | Общее на проект | Правило проекта «пишет общее состояние — бэк». Чинит расхождение между операторами, делает `readProjectProperty` осмысленным без монитора |
| Права на процедуру | Любой оператор, `sessionId` — только подпись | На станции есть и местный пульт, и операторская; запрет «второму нельзя» вреден. Владение — политика доступа, решается отдельно |
| Хранение состояния | Своя схема `runtime` | Прецедент — схема `automation`. `runtime` перестаёт быть безсостоянийным по условию задачи, значит владеет своим состоянием сам, а не просит `editor` |
| `project_data_table` под состояние | Нет | Это пользовательский документ: его правит оператор руками и читают все скрипты через `data()`. Состояние движка не должно быть редактируемым документом |
| Владение | Аренда драйвера в БД, один экземпляр на этапе 1 | Единица масштабирования — драйвер, потому что теги проекта размазаны по партициям одного топика и владение по партициям не выравнивается |
| Переходный период для фронта | Нет, ломаем сразу | Решение пользователя. Контракт для фронта выносится отдельным документом |

### Почему единица масштабирования — драйвер

Kafka-ключ телеметрии — путь тега (`Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST`), поэтому
теги одного проекта равномерно раскиданы по всем партициям `scada.tags`. Владение
проектами по партициям, как в `automation` (там топик определений ключуется по
`projectId`), здесь невозможно.

Первый сегмент пути — драйвер, то есть группа контроллеров. В `controllers.yaml` шлюза
теги сгруппированы по протоколам и контроллерам, и все теги контроллера «Phoenix Contact»
начинаются с `Барановичи-1`. В базе у проекта BN1_MCA1 все 443 привязанных свойства имеют
этот корень и ни одного чужого. Значит правило «проект принадлежит драйверу» проверяемо
на данных.

Модель владения: **экземпляр владеет набором драйверов**, в обычном случае одним.
Формулировка «один экземпляр = один топик» жёстче, чем нужно: проект, которому
понадобятся теги двух ПЛК, при ней стал бы невозможен.

**Потолок, который надо знать:** драйвер разделить нельзя. Если у одного ПЛК окажется
больше проектов и скриптов, чем тянет экземпляр, единственный выход — дробить сам драйвер
в `controllers.yaml`.

## Архитектура

### Жизненный цикл проекта

`editor` публикует проекты «в эксплуатации» компактным топиком с ключом `projectId` — тем
же способом, каким уже публикует определения автоматизации. `runtime` на старте вычитывает
топик до конца и только потом начинает тикать: иначе первые секунды он работал бы с
неполным набором проектов.

`ProjectRuntime` — `projectId`, `TagSubscriptionIndex`, `ProjectData`, общая карта
`propertyValues`, активные процедуры. Строится теми же вызовами, что сейчас делает
`RuntimeSessionService.createSession`, но один раз на проект.

Интерес к тегам в `TagValueRouter` объявляет проект, а не сессия. Набор драйверов
выводится из путей тегов дерева и логируется; на этапе 1 все драйверы отображаются в
единственный `scada.tags`, на этапе 2 набор станет списком топиков.

Гасит проект только снятие флага в `editor`. Не уход оператора, не закрытие WebSocket,
не `RuntimeSessionReaper`. При гашении: остановить процедуры с записью состояния, снять
интерес к тегам, освободить память. Незавершённая процедура в момент гашения пишется в
лог отдельным предупреждением.

### Восстановление

На старте, после списка проектов, `runtime` поднимает из `runtime.procedure_state`
незавершённые процедуры активных проектов и продолжает с сохранённого шага. **Действия
шага не переприменяются** — мойка уже в этом состоянии, повторная запись дёрнула бы
клапаны. Условие переоценивается на первом же тике.

### Поток событий

`on_change` считается один раз на проекте и пишет в общую `propertyValues`; наблюдателям
рассылается результат. Значения тегов и изменения свойств кладутся в исходящий буфер
каждой сессии проекта — буферы и `OutboundFlusher` остаются посессионными, чтобы зависший
клиент портил только себе.

События процедуры публикуются проектом всем наблюдателям и получают два новых поля: `by`
(имя из `X-Username`) и `sessionId` того, кто нажал.

Наблюдателей может не быть — тогда события некому доставить, и буферизации «на будущее»
нет: мойка, копящая события сутки в памяти, это утечка. Поэтому переходы шагов,
`WRITE_FAILED` и `STALLED` **логируются на уровне сервиса** (`INFO`/`WARN`), а не только
уходят в кадр. Без клиентов лог — единственный след происходящего.

Снимок при подключении берётся после постановки сессии в рассылку: обратный порядок терял
бы изменения между снимком и подпиской. Возможный дубль безвреден — фронт перезаписывает
значение по ключу.

## Контракт API

Процедуры адресуются проектом:

| Было | Стало |
|---|---|
| `POST /recipes/{id}/start` `{sessionId}` | `{projectId, sessionId?}` |
| `POST /recipes/{id}/confirm` `{sessionId}` | `{projectId, sessionId?, stepIndex?}` |
| `POST /recipes/{id}/jump` `{sessionId, stepIndex}` | `{projectId, stepIndex, sessionId?}` |
| `POST /recipes/{id}/abort` `{sessionId}` | `{projectId, sessionId?}` |
| `GET /recipes/{id}/status?sessionId=` | `?projectId=` |
| `GET /recipes/{id}/resume-guess` | **удалён** |

`projectId` обязателен — это ключ. `sessionId` необязателен и нужен только чтобы сказать,
из какого экрана нажали. Прав на процедуру он не даёт.

`stepIndex` в `confirm` — **необязательный**. Если фронт его прислал, это шаг, который
оператор видел на экране, и при несовпадении с текущим приходит `409` с актуальным
статусом. Если не прислал — подтверждается текущий шаг, как сейчас. Поле существует на
случай, когда два оператора подтверждают почти одновременно и второй закрывает уже
следующий шаг; решено, что на практике так не совпадёт, поэтому фронт не обязан его
поддерживать.

Коды: `409` на `start` идущего рецепта (в теле — текущий статус), `409` на любой вызов
процедуры проекта не в эксплуатации, `409` на несовпавший `stepIndex`, если он передан,
`404` на неизвестный `recipeId`.

`resume-guess` удаляется вместе со всем кодом подсказки: он существовал только потому, что
состояние терялось при перезапуске. Держать рядом точный механизм и гадалку — значит
обрекать кого-то однажды поверить гадалке.

Сессия: `POST /sessions {projectId}` по-прежнему отдаёт `sessionId`, `wsPath` и дерево, но
ничего не поднимает. Проект не в эксплуатации — `409` с внятным текстом: состояние
«проект выключен» должно быть видимым, а не выглядеть неисправностью экрана.
`DELETE /sessions/{id}` закрывает только соединение.

Первый кадр WebSocket — `SNAPSHOT` с текущими значениями тегов проекта, картой
`propertyValues` и списком активных процедур с их шагами. Дальше — привычные `UPDATE`.

Не меняются: `POST /tags/write` (`sessionId` становится необязательным),
`GET /sessions/{id}/snapshot?componentId=`, запуск `ACTION`-скриптов.

## Модель хранения

У `runtime` сегодня нет ни JPA, ни datasource — в `build.gradle.kts` и `application.yml`
нет ни строки про базу. Это не «добавить таблицу», а завести сервису персистентность с
нуля: зависимость, конфигурация, схема.

Схема `runtime` в базе `savushkin`, `ddl-auto: update`, `default_schema: runtime`. Саму
схему Hibernate не создаёт — создаётся руками, как `editor`/`channel`/`automation`; это
пункт инструкции развёртывания.

**`procedure_state`** — только активные процедуры:

| Колонка | Смысл |
|---|---|
| `project_id`, `recipe_id` | ключ, `UNIQUE (project_id, recipe_id)` |
| `step_index` | текущий шаг |
| `step_entered_at` | время входа — из него восстанавливается `elapsedMs` |
| `confirmed` | ручное подтверждение текущего шага |
| `accumulated_actions` | `jsonb`, накопленное состояние тегов шагов `0..N` (его пишет `jump`) |
| `started_by`, `started_at` | кто и когда запустил |
| `version` | оптимистическая блокировка |

Пишется на каждом переходе шага. Частота нормальная: у «Дезинфекции» 28 шагов за 36 минут,
самые быстрые шаги-сбросы закрываются за секунду. `accumulated_actions` для неё — 22 тега.

Завершённая или прерванная процедура строку удаляет. Журнала моек в этапе 1 нет.

`version` нужен уже при одном экземпляре: он ловит расхождение памяти и базы, если аренда
разъехалась. Молча перезаписать чужое состояние мойки — худшее, что тут может случиться.

**`driver_lease`** — `driver` (`UNIQUE`), `instance_id`, `acquired_at`, `renewed_at`.

Аренда берётся **после** вычитывания списка проектов и вывода из их деревьев набора
драйверов — раньше экземпляр просто не знает, что ему нужно. На каждый свой драйвер
экземпляр захватывает строку и продлевает её, пока работает.

Драйвер занят другим живым экземпляром — **проекты этого драйвера не поднимаются**, в лог
идёт предупреждение с именем держателя. Сервис при этом стартует и обслуживает HTTP: отказ
поднимать чужие проекты и отказ запускаться — разные вещи, и второе оставило бы оператора
без диагностики. На этапе 1, когда экземпляр один, он забирает все драйверы и ни с кем не
спорит. На этапе 2 та же таблица становится распределением драйверов между экземплярами,
без переделки.

**Не храним:** `propertyValues` (писать в базу на каждое изменение тега — это поток
телеметрии, не место для БД) и значения тегов. Следствие, которое надо знать: после
перезапуска `runtime` состояние свойств вернётся к начальным значениям дерева и наполнится
заново по мере прихода телеметрии и срабатывания `on_change`. Для редко меняющихся свойств
это означает временно неверную картинку на мнемосхеме.

## Тестирование

Тесты минимальные, по одному на риск; остальное проверяется руками на стенде прогоном
«Дезинфекции». У `runtime` сейчас 22 теста и нет базы — с появлением схемы понадобится
Testcontainers, как в `editor` и `auth`.

1. Процедура переживает закрытие сессии: старт, закрыть сессию, дождаться условия — шаг перешёл.
2. Восстановление после перезапуска: продолжает с сохранённого шага и **не переприменяет** действия.
3. `409` на повторный `start` идущего рецепта, ПЛК не тронут.
4. `on_change` при двух наблюдателях исполняется один раз.
5. Аренда драйвера: чужой драйвер занят — проекты этого драйвера не поднимаются, в логе имя держателя.

## План работ

1. Персистентность в `runtime`: зависимость, datasource, схема, `procedure_state`, `driver_lease`, захват аренды на старте.
2. `ProjectRuntime` и жизненный цикл: флаг в `editor`, публикация, потребление, поднятие и гашение, интерес к тегам от проекта, вывод драйверов.
3. Состояние свойств и `on_change` на проект: правка `TagValueRouter` и `OnChangeDispatcher`, снятие кратности исполнения.
4. Процедуры на `projectId`: смена ключа, сохранение и восстановление, `409`, необязательный `stepIndex` в `confirm`, удаление `resume-guess`.
5. Сессия-наблюдатель: `SNAPSHOT`, рассылка проектом, автор в событиях, логирование переходов.
6. Документация: `CLAUDE.md` (у `runtime` появилась БД; `runtime` однооэкземплярный), `docs/API.md` (раздел RUNTIME устарел — попутно закрывается `scada-536`), `docs/modules/runtime.md`, `docs/integration/2026-09-16-runtime-project-scope.md` для фронта, пункт про создание схемы в развёртывании.
7. Beads: журнал моек; этап 2 (топики на драйвер, несколько экземпляров, маршрутизация в `gateway`); снимок `propertyValues`.

Каждый пункт оставляет систему в рабочем состоянии, кроме 4 и 5 — они ломают контракт для
фронта и должны выехать вместе с документом для него.

## Риски

- **Монитор не работает, пока фронт не поправят.** Переходный период отклонён осознанно.
  Контракт для фронта — часть работы, а не приложение к ней.
- **`runtime` на этапе 1 однооэкземплярный по правилу.** Сегодня он такой по факту: все
  consumer-ы тегов сидят в одной группе `runtime-service` и делают `subscribe`, поэтому
  второй экземпляр уже сейчас молча отбирает половину партиций у первого. Аренда драйвера
  делает это видимым: второй экземпляр честно скажет, что проекты уже крутит другой. Но
  телеметрию он всё равно будет забирать — это чинится только на этапе 2, отдельной группой
  Kafka у каждого экземпляра. До тех пор второй экземпляр поднимать нельзя.
- **Флаг «в эксплуатации» — новая ручка, которую можно забыть нажать.** Проект без флага
  выглядит мёртвым. Отсюда требование к тексту `409`: он должен называть причину.
