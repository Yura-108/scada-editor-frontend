# Контракт: аргументы действия (`ACTION.args`) и меню выбора в мониторе

Дата: 02.10.2026. Backend-часть готова и протестирована (`runtime`, ветка `feat/action-args`,
`scada-dscl`). Фронт (scada-editor-frontend) — отдельная задача в том репозитории; ниже — точный
контракт и что именно поменять.

## Коротко: что и зачем

До сих пор `ACTION` нёс только `scriptId`: «запусти скрипт N». Серверный скрипт не получал от
клика никаких данных, поэтому выбор оператора приходилось размножать скриптами («Рецепт 4»,
«Рецепт 5», … — по скрипту на вариант).

Теперь у `ACTION` есть необязательное поле `args` — JSON-объект. Серверный скрипт видит его
объектом `args`. Первый потребитель — выбор рецепта для танка (`scada-s7hu`, старый `prj.SetProd`):
меню строится из тега `RECMAN[1].LIST`, выбранный номер уходит в один скрипт аргументом.

## 1. WebSocket: сообщение `ACTION`

```json
{ "type": "ACTION", "scriptId": 123, "args": { "recipe": 4 } }
```

| Поле | Обязательно | Что |
|---|---|---|
| `type` | да | `"ACTION"` |
| `scriptId` | да | числовой id серверного скрипта компонента (как раньше) |
| `args` | нет | JSON-**объект**; значения — любые JSON (число, строка, bool, null, вложенные) |

Правила:

- Нет `args`, `null` или `{}` — скрипт видит пустой объект `{}`. Старые сообщения без `args`
  работают как раньше.
- `args` — только объект. Массив, строка или число в `args` — сообщение не разбирается целиком и
  отбрасывается (в логе runtime `Malformed message`), ответа нет.
- Сериализованный `args` длиннее **4096** символов — действие отклоняется: скрипт не запускается,
  в журнале действий строка `outcome: ERROR`, ответа нет. Аргументы — это выбор из меню, а не данные.
- Ответ на `ACTION` не изменился: `UPDATE` с `tags = null` и изменившимися `properties`, только
  нажавшему; остальным мониторам — обычным батчем.
- Дедупликация повторов (окно `runtime.script.action-min-interval-ms`, 300 мс) теперь учитывает `args`: тот же
  скрипт с **другими** аргументами следом — не дребезг и выполняется. Тот же скрипт с теми же
  аргументами в окне — отбрасывается, как раньше.

## 2. Серверный скрипт (`scripts.script`): объект `args`

```js
// «Загрузить рецепт» на Танк_Продукт сцены «Продукция» (Танк 1 → техобъект N = 2)
const r = Number(args.recipe);
if (!Number.isInteger(r) || r < 1 || r > 15) return;   // проверять аргумент — дело скрипта
writeTag('PRODUCT_TYPE', r);          // TANK1.TANK.S_PAR_F[ 8 ] — «Тип продукта»
writeTag('RECMAN_CMD', 1000 * 2 + r); // STATION.RECMAN[1].CMD
```

- `args` — свежий объект на каждый запуск; правка его ни на что не влияет.
- В `on_change` `args` всегда `{}`, в условиях шагов процедур — `null`: контексты GraalVM общие,
  аргументы прошлого действия в них не протекают.
- Аргумент пришёл с фронта — доверять ему как вводу оператора: проверять диапазон в скрипте.

## 3. Журнал действий

`GET /api/runtime/actions`: у строки `kind: "ACTION"` поле `tags` теперь — аргументы:

```json
{ "kind": "ACTION", "component": "Танк_Продукт", "target": "Загрузить рецепт",
  "tags": [ { "arg": "recipe", "value": 4 } ], "outcome": "OK" }
```

Без аргументов `tags` — `null`, как раньше. Что записал скрипт, по-прежнему видно в архиве.

## 4. Что поменять на фронте

### 4.1. `runtimeConnection.sendAction`

```ts
sendAction: (scriptId: number, args?: Record<string, unknown>) => {
  if (ws?.readyState === WebSocket.OPEN) {
    ws.send(JSON.stringify(args ? {type: "ACTION", scriptId, args} : {type: "ACTION", scriptId}));
  } else { /* как сейчас */ }
},
```

### 4.2. `runScript(name, args?)` в `onClick`

`useRuntimeEngine.runScriptOn(el, name, args?)` прокидывает `args` в `sendAction`. В песочнице
`onClick` — `runScript("Имя", { recipe: 4 })`; вызов без второго аргумента работает как раньше.
Подтверждение клика монитором — как у любого `runScript`; в тексте подтверждения уместно показать
выбранный пункт («Загрузить рецепт: молоко?»).

### 4.3. Меню выбора из `onClick` — `showMenu(items)`

Нужно, чтобы `onClick` построил меню **из значения тега** и по выбору запустил серверный скрипт
с аргументами. Предлагаемая функция в песочнице `onClick`:

```ts
showMenu(items: Array<{ label: string; script: string; args?: Record<string, unknown> }>): void
```

- рисует всплывающее меню у точки клика (тот же вид, что меню монитора по скриптам `displayed`);
- выбор пункта → `runScript(item.script, item.args)` (с обычным подтверждением);
- пустой `items` — ничего не показывать; Esc / клик мимо — закрыть без действия.

Пример `onClick` для `Танк_Продукт` (свойство `LIST` с тегом `STATION.RECMAN[1].LIST`
добавляется на тот же компонент):

```js
// БЫЛО: prj.SetProd(TankObj1) — меню имён из RECMAN.List, «Имя?», затем S_PAR_F8 и CMD
const items = String(LIST.V || '')
  .split('||')
  .filter(Boolean)
  .map(s => s.split('##'))                       // "4##test" → ["4", "test"]
  .filter(([n, name]) => name && name !== 'none')
  .map(([n, name]) => ({ label: `${n}. ${name}`, script: 'Загрузить рецепт', args: { recipe: Number(n) } }));
showMenu(items);
```

Формат `LIST` (ptusa `ParamsRecipeManager`): `номер##имя||номер##имя||…`, только рецепты с `ACT = 1`;
`none` — незаполненный слот. Разбор — в `docs/RECIPES_RECMAN.md`.

## 5. Чего нет и не будет

- Ответа «скрипт отклонён» фронту нет — как и для остальных отказов `ACTION` (они видны в
  `/api/runtime/diagnostics/script-failures` и журнале действий).
- `args` не передаются в `on_change` и процедуры — это аргументы именно клика.
