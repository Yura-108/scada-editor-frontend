# Контракт: несколько экземпляров runtime — что меняется на фронте

Дата: 17.09.2026. Бэкенд — `main`, коммит `16612e0`. Проверено на стенде: два экземпляра runtime
(8085, 8095) за одним gateway — монитор, процедура, запись тегов, снятие проекта, остановка экземпляра.

Опирается на контракт [2026-09-16-runtime-project-scope.md](2026-09-16-runtime-project-scope.md)
(проект вместо сессии) — он в силе.

## Коротко

Сервер мониторинга (`runtime`) теперь может работать в нескольких экземплярах. Топики телеметрии и
проекты назначаются экземплярам вручную. Фронт по-прежнему ходит через gateway на один адрес: запрос
по чужому проекту экземпляр сам пересылает владельцу. Правок немного, но две из них обязательны.

## Что сделать

1. **Подключать WebSocket только через gateway и только по `wsPath` из ответа.**
   Сейчас `runtimeConnection.ts` берёт `wsPath` как есть — это правильно. Проверить, что
   `NEXT_PUBLIC_RUNTIME_WS_URL` нигде не указывает прямо на runtime (`:8085`): по умолчанию там
   `ws://localhost:8080`, это gateway. Комментарий в `src/app/api/runtime/sessions/route.ts` про прямое
   подключение к `:8085` устарел.
2. **Не разбирать `sessionId`.** Теперь это `<instanceId>.<uuid>`, а не голый UUID. Никаких проверок
   формата и склейки пути из него.
3. **Показывать новые `409` и `503` текстом с бэкенда.** Плашка монитора уже показывает `message` —
   для `409` это работает без правок. Отдельно обработать `503`: «сервер исполнения недоступен»,
   повтор с паузой.
4. **Учесть статус записи `NO_TOPIC`** — показывать как отказ записи: команда в ПЛК не ушла.

## 1. Сессия и WebSocket

`POST /api/runtime/sessions` → `200`:

```json
{
  "sessionId": "runtime-1.3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "wsPath":    "/ws/runtime/runtime-1/runtime-1.3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "projectTree": { }
}
```

- **`sessionId`** — непрозрачная строка. Передаётся обратно как есть: в `snapshot`, `DELETE`, в тела процедур.
- **`wsPath`** — `/ws/runtime/<instanceId>/<sessionId>`. Подключение:
  `ws://<gateway>${wsPath}?token=<jwt>`. gateway выбирает экземпляр по `instanceId` в пути.
- **Путь, собранный вручную** (`/ws/runtime/${sessionId}`), больше не существует — gateway не найдёт
  маршрут. Подключение к чужому экземпляру закрывается кодом `1003` «Session belongs to instance …».
- **Перезапуск экземпляра:** сессии живут в памяти экземпляра, после его перезапуска нужен новый
  `POST /sessions`, как и раньше.

## 2. Новые ответы

Касаются всех запросов с проектом: `POST /sessions`, `GET /sessions/{id}/snapshot`,
`DELETE /sessions/{id}`, `/api/runtime/recipes/**`, `POST /api/runtime/tags/write`,
`POST /api/automation/projects/{id}/data/reload`. В теле всегда есть `message`; разные `409`
различаются только по нему.

| Код | `message` | Когда | Что показать |
|---|---|---|---|
| `409` | Проект 8501 не назначен ни одному экземпляру runtime | проект не распределён администратором | текст с бэкенда. Это **не** «не введён в эксплуатацию» — у того свой текст |
| `409` | Проект не назначен этому экземпляру runtime (…): назначение только что сменили — повторите запрос | запрос попал в момент переноса проекта | можно молча повторить один раз |
| `503` | Экземпляр runtime-1, на котором работает проект, недоступен | экземпляр-владелец остановлен или не отвечает | «Сервер исполнения недоступен». Проект никто не подхватывает — повторять с паузой |
| `503` | Экземпляр runtime-1, на котором работает проект, неизвестен | сессия от экземпляра, которого нет в списке | как выше; монитор открыть заново |

## 3. Запись тегов

`POST /api/runtime/tags/write` — формат прежний, добавлены два исхода:

- статус элемента **`NO_TOPIC`**: путь тега не покрыт топиками экземпляра, команда в ПЛК **не
  отправлена**; `success: false`, в `message` — путь;
- если путь **первого** тега не покрыт ничьим топиком, весь запрос отвечает `409`
  «Путь … не покрыт топиками ни одного экземпляра runtime».

```json
[
  { "tagId": "Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST", "success": true, "status": "APPLIED" },
  { "tagId": "Минск-1.PLC.X", "success": false, "status": "NO_TOPIC",
    "message": "Путь не покрыт топиками экземпляра: Минск-1.PLC.X" }
]
```

## 4. API назначений — для будущего экрана администратора

Экран не обязателен: назначения сейчас делаются запросами. Всё идёт через gateway с токеном;
применяется за 5 секунд.

| Метод | Путь | Тело / ответ |
|---|---|---|
| `GET` | `/api/runtime/instances` | список экземпляров (пример ниже) |
| `PUT` | `/api/runtime/instances/{id}/topics/{telemetryTopic}` | `{commandsTopic, resultsTopic, pathPrefixes: []}` → `204` |
| `DELETE` | `/api/runtime/instances/{id}/topics/{telemetryTopic}` | → `204` |
| `PUT` | `/api/runtime/instances/{id}/projects/{projectId}` | → `204` |
| `DELETE` | `/api/runtime/instances/{id}/projects/{projectId}` | → `204` |

```json
[{
  "instanceId": "runtime-1",
  "baseUrl": "http://10.0.0.11:8085",
  "description": null,
  "lastSeenAt": "2026-09-17T12:55:51Z",
  "topics": [{
    "telemetryTopic": "scada.tags",
    "commandsTopic": "scada-commands",
    "resultsTopic": "scada-command-results",
    "pathPrefixes": ["Барановичи-1"]
  }],
  "projects": [8501]
}]
```

- `409` с `message` — топик, командный топик или проект уже у другого экземпляра, либо префикс
  пересекается с чужим.
- `409` с `uncoveredPaths: [...]` — теги проекта не покрыты топиками экземпляра; показать список путей.
- `404` — экземпляр ни разу не запускался; `400` — нет префиксов или снимается то, что не назначено.
- Перенос проекта — два запроса: `DELETE` у старого экземпляра, `PUT` новому. Запроса «переместить»
  нет намеренно.
- `lastSeenAt` старше ~30 секунд — экземпляр, скорее всего, не работает.

## 5. Без изменений

Протокол WebSocket (`SNAPSHOT`, `UPDATE`, `ACTION`, `SUBSCRIBE_TASKS`, `PING`), закрытие `1001` при
выводе проекта из эксплуатации, тела процедур, `GET /api/automation/projects/{id}/tasks`, флаг
«в эксплуатации» в editor.
