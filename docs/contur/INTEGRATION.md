# CONTUR → редактор мнемосхем: что мы отдаём и как это рисовать

Документ для тех, кто принимает наши `*.json`. Здесь описано, **как схема
выглядит у нас в приложении после загрузки Lua, открытия PDF и разметки** —
и какой элемент файла за что отвечает. Если рисовать по этим правилам,
в редакторе получится та же картинка.

Разделы 1–4 — про отрисовку, раздел 5 — **про данные**: положение каждого
устройства в операциях, связность по трубам и всё остальное, что знает
конвейер. Раньше за этим приходилось идти в наш XML.

Файл собран по вашей спецификации импорта (`IMPORT_SCHEME_SPEC.md`) —
ссылки на её разделы даны по тексту. Разбор трёх замечаний к прошлым файлам
(ромбы, обрывы, размер кружков) — в `ОТВЕТ-ПО-ОТРИСОВКЕ.md`.

Формат самого файла (плоский массив, ключи, `null`, порядок полей) описан
в `PROJECT.md`, §6.2.

---

## 1. Откуда берутся данные

| Источник | Что даёт |
|---|---|
| `main.io.lua`, `main.wago.lua` | устройства контроллера: имя (`LA_TANK1V1`), тип (`V`, `LS`, `TE`…), артикул, описание |
| `main.objects.lua` | технологические объекты (танки, линии, CIP), их операции и состояния |
| PDF Eplan | векторный чертёж: линии, прямоугольники, кривые, текстовые обозначения |
| Модель YOLO | рамки устройств на чертеже (`valve` / `sensor` / `pump`) |

Дальше конвейер связывает одно с другим: замкнутые контуры на чертеже
получают имена техобъектов, текстовые обозначения (`-V1`, `LS2`) — имена
устройств из Lua. Результат этой связи и уезжает в файл.

Главное, что стоит понимать: **чертёж и наши данные — два разных слоя.**
Линии — это перерисованный PDF. Кружки, рамки и подписи — то, что мы
про этот чертёж поняли.

## 2. Система координат

Файл собран под ваш холст, а не под печатный лист — по `IMPORT_SCHEME_SPEC`,
§2 и §3.

- **Единица — пиксель холста.** Лист масштабирован одним коэффициентом
  `k = 40 / d`, где `d` — типовой размер символа устройства на этом листе
  (он записан в нашей разметке). Для A0 это 31.32 пункта, `k = 1.277`;
  для листа 13 mozzarella `k = 1.297`. Смысл коэффициента ваш: символ должен
  занять две клетки.
- **Начало — левый верхний угол, ось Y вниз.** Схема сдвинута в начало
  координат: содержимое начинается у `(0, 0)`, сдвиг кратен клетке.
- **Габарит схемы** после масштаба: A0 — 4340×3060, лист 13 mozzarella —
  3120×2220. Оба влезают в мир 5000×5000, и это проверяется у нас.
- **Сетка 20.** Всё, что человек двигает, стоит в узлах: группы, рамки,
  кружки устройств, тексты. Чертёж выровнен мягче — см. §4.1.
- **Процентов в файле нет.**

**Точка привязки `x, y` зависит от типа:**

| Тип | Что означают `x, y` |
|---|---|
| `line` | середина отрезка (геометрия — в `x1, y1, x2, y2`) |
| `circle` | **центр** круга, как в диалекте CONTUR; ваш нормализатор вычитает радиус |
| `rectangle` | левый верхний угол |
| `text` | левый верхний угол строки |
| `group` | левый верхний угол; координаты детей локальные |

Множитель и сдвиг записаны в элементе `meta` (`canvas.scale`, `canvas.origin`),
исходный размер листа в пунктах — там же (`sheet`).

## 3. Слои и порядок отрисовки

**Элементы в файле идут в порядке отрисовки**, достаточно рисовать подряд:

1. `meta` — данные о листе, не фигура (§5.4);
2. рамки техобъектов — `rectangle`;
3. чертёж — `line`;
4. надписи чертежа — `text` с `drawing`;
5. устройства — `circle`;
6. наши подписи — `text`.

Внутри группы порядок задаёт её массив `children`, и первым там всегда
идёт рамка-`rectangle`.

## 4. Что чем рисуется

### 4.1 Линия чертежа — элемент `line` с полем `contur_color`

Перерисованный PDF, самый многочисленный вид элементов.

| | |
|---|---|
| Геометрия | `x1, y1, x2, y2` — концы. `x, y` — середина, `w, h` — габарит; для отрисовки не нужны |
| Цвет | `borderColor` (`#e53935` или `#1e88e5`) |
| Толщина | `stroke_width`, ступенями 1 / 2 / 3 |
| Смысл | `contur_color`: «blue» — трубопровод, «red» — контур устройства, найденного моделью. Своё поле, потому что `color` у вас заливка (§6 вашей спецификации) |
| Ссылки | `line_id` — наш номер сегмента; у синих ещё `pipeline_id` и `pipeline_name`, у красных `device_name` |
| Рамка листа | `frame: true` — рамка чертежа и разлиновка штампа; `line_id` у них нет |

**Про сетку.** Ортогональный отрезок посажен на узлы, если это смещает конец
не больше чем на полклетки и отрезок не схлопывается. Диагонали и звенья
разложенных кривых оставлены точными — по вашему §3.1. На контрольном листе
из 5003 ортогональных на сетку село 2921.

Кривые из PDF разложены на звенья с допуском в один пункт: 784 кривые дали
2112 отрезков. Раньше кривая уезжала одной хордой и срезала угол на 3–6 пунктов.

### 4.2 Рамка техобъекта — элемент `rectangle` с полем `contour: true`

Прямоугольник, охватывающий танк, линию или шкаф.

| | |
|---|---|
| Геометрия | `x, y` — левый верхний угол, `w, h` — размер; всё кратно клетке |
| Цвет | `strokeColor` — по имени техобъекта из палитры десяти цветов |
| Отличие | есть `contour: true` и `tech_object`, `label` пустой — имя идёт отдельным текстом |

Цвет идёт в `strokeColor`, а не `borderColor`: по §6 `borderColor` вы
переводите только у линии, круга и текста.

### 4.3 Устройство — элемент `circle`

| | |
|---|---|
| Геометрия | центр `x, y` в узле сетки, `radius` кратен 20 и не меньше 20, `w = h = 2·radius` |
| Цвет | `bg` и `borderColor` — по типу устройства (таблица ниже) |
| Размер | из рамки, найденной моделью, в пределах 0.5–1.5 от обычного символа листа, затем округлён до клетки |
| Смысл | `lua_name` — полное имя из контроллера, `pdf_name` — обозначение с чертежа, плюс `tech_object`, `device_type`, `confidence`, `descr`, `article`, `category`, `subtype`, `dtype` и всё, что пришло из Lua |
| Данные | `contur_states` — положение в каждой операции (§5.1), `connected_devices` — соседи по трубам (§5.3) |

Цвета по типу устройства — те же, что у нас в окне:

| Тип | Цвет | Тип | Цвет |
|---|---|---|---|
| `V` клапан | `#e74c3c` | `LS` уровень (дискретный) | `#8e44ad` |
| `M` насос | `#34495e` | `LT` уровень (аналоговый) | `#9b59b6` |
| `DI` / `DO` | `#3498db` / `#2980b9` | `TE` температура | `#1abc9c` |
| `AI` / `AO` | `#2ecc71` / `#27ae60` | `PT` / `PC` давление | `#f39c12` / `#7f8c8d` |
| `QT` | `#d35400` | `FQT` расход | `#c0392b` |
| `GS` | `#16a085` | `SB` кнопка | `#2c3e50` |
| `HL` / `HLA` лампа | `#f1c40f` / `#f39c12` | `G` | `#95a5a6` |

Остальные типы — чёрный `#000000`.

### 4.4 Подпись устройства — `text` без `contour` и без `drawing`

| | |
|---|---|
| Строка | в полях `text` и `label` |
| Содержание | обозначение с чертежа, а при неполной уверенности модели — она в скобках: `-V1 (0.9)` |
| Положение | на клетку вправо и на клетку вверх от центра устройства |
| Кегль | `font_size: 12` |
| Связь | `lua_name` и `tech_object` |

Сдвиг взят целыми клетками намеренно: сдвиг меньше клетки привязка съедала,
и подпись ложилась на сам кружок.

### 4.5 Имя техобъекта — `text` с `contour: true`

То же самое, но `font_size: 16` и цветом своего контура. Положение —
две клетки влево и одна вверх от центра контура.

### 4.6 Надпись чертежа — `text` с `drawing: true`

Обозначения Eplan, номера позиций, штамп листа — весь текст исходного PDF.
Раньше их в файле не было вовсе, и схема приезжала безымянной.

| | |
|---|---|
| Строка | в `text` и `label` |
| Кегль | `font_size` — из чертежа с масштабом, но не меньше 12 |
| Цвет | `borderColor`; `contur_color` — «red», если надпись внутри рамки устройства |
| Отличие от наших подписей | есть `drawing: true`, **нет** `lua_name` и `tech_object` |
| Положение | левый верхний угол строки (в SVG хранится базовая линия, мы вычли 0.8 кегля) |

На A0 таких 779, на листе 13 mozzarella — 196.

## 5. Данные, а не картинка

Всё, что ниже, — не про отрисовку. Это то, ради чего файл нужен: что
за устройство, в каких операциях оно участвует, с чем соединено. Раньше
за этим приходилось идти в наш XML.

### 5.1 Положение устройства в операциях — `contur_states`

Своим полем, а не штатным `states`. По вашему §7 в `states` полагается ровно
одно состояние с пустым `overrides` — иначе базовые `x/y/w/h` при отрисовке
игнорируются, а у одного клапана таких состояний бывает восемьдесят, и схему
бы сдвинуло. Поэтому `states` мы шлём как вы просите (одно «Нормальное»,
`overrides` пустой), а данные — рядом:

```json
"contur_states": [
  { "name": "Мойка / Состояние 1 / шаг 1 На МГ — открыто",
    "overrides": { "bg": "#2ecc71", "borderColor": "#e74c3c" },
    "status": "opened", "status_text": "открыто",
    "operation_id": "2_1", "operation": "Мойка",
    "operation_object": "Танк", "operation_object_id": "2",
    "state_id": "2_1_1", "state": "Состояние 1",
    "step_id": "2_1_1_1", "step": "На МГ", "step_number": 1 } ]
```

| Поле | Что означает |
|---|---|
| `status` | `opened` или `closed` |
| `status_text` | то же по-русски |
| `operation_id`, `operation` | операция: идентификатор и название |
| `operation_object`, `operation_object_id` | чья это операция |
| `state_id`, `state` | состояние операции |
| `step_id`, `step`, `step_number` | шаг; **этих трёх полей может не быть** — устройство бывает открыто состоянием целиком |
| `overrides` | как показать положение, если захотите: заливка зелёная открыто, красная закрыто |

Что стоит знать:

- **имена уникальны внутри элемента.** Имена объектов в описании операций
  не уникальны — «Танк» носят все восемь, — поэтому при совпадении к имени
  дописан идентификатор операции;
- **одно устройство участвует в операциях разных объектов.** Клапан
  CIP-коллектора встречается и в мойке танка, и в мойке линии выдачи —
  так в конфигурации контроллера, это не ошибка;
- по `operation_id` состояние ссылается на программу операции
  в `meta.operations` (§5.2).

Сколько их: A0 — **1911 состояний** у 233 устройств, 64 операции; лист 13
mozzarella — 63 у 35 устройств, 8 операций.

Отдельно: если перед выгрузкой в нашем окне выбрана операция, у устройства
появляются поля `operation_state` («открыто» / «закрыто» / «не используется»),
`operation_state_name`, `operation_step`, `operation_step_number`.

### 5.2 Программы операций — `meta.operations`

То, что стоит за состояниями: операция, её состояния и шаги, а у каждого
шага — какие устройства он открывает и какие закрывает.

```json
{ "id": "2_1", "name": "Мойка", "tech_object": "Танк",
  "base_operation": "CIP",
  "states": [ { "id": "2_1_1", "name": "Состояние 1",
                "steps": [ { "number": 1, "name": "На МГ",
                             "opened_devices": ["TANK1V1", "TANK1V2"],
                             "closed_devices": ["TANK1V11"] } ] } ] }
```

В файл попадают только операции, в которых участвуют устройства этого листа.
Списки устройств в шагах полные, как в конфигурации: там могут быть имена,
которых на этом листе нет — техобъект разложен по нескольким листам.

### 5.3 Связность: чем соединены устройства

| Где | Поле | Что означает |
|---|---|---|
| линия трубы | `pipeline_id`, `pipeline_name` | к какому трубопроводу относится отрезок |
| устройство | `connected_devices` | с какими устройствами оно соединено трубами |
| `meta.pipelines` | | трубопроводы листа: номер, имя, число сегментов, длина, устройства на концах |
| `meta.connections` | | граф связей: труба и устройства, которые она соединяет |
| `meta.graph` | | сводка: связей, коллекторов, тупиков |

Сегменты трубопровода в `meta` не повторяются: это и есть элементы `line`
с проставленным `pipeline_id`. На A0 — 767 труб, 250 связей;
`connected_devices` есть у 164 устройств из 233.

### 5.4 Элемент `meta` — данные о листе целиком

Первый элемент массива. Не фигура: `visible: false`, `w = h = 0`, тип `meta`,
метка `contur_meta: true`.

| Поле | Что внутри |
|---|---|
| `format`, `version` | «CONTUR HMI» и версия состава файла |
| `canvas` | габарит схемы, единицы, шаг сетки, масштаб и сдвиг |
| `sheet` | исходный размер листа в пунктах PDF |
| `counts` | сколько элементов какого типа |
| `tech_objects` | техобъекты листа: рамка, устройства, операции |
| `pipelines`, `connections`, `graph` | связность (§5.3) |
| `junction_points` | точки касания трубы и контура устройства |
| `operations` | программы операций (§5.2) |
| `current_operation` | выбранная операция и сколько в ней открыто и закрыто |

Точек сопряжения много — 4713 на A0, это 0.65 МБ файла; если не нужны,
скажите, уберём.

## 6. Почему у устройства две фигуры

Частый вопрос: рядом с прямоугольником стоит кружок.

Это не сбой, а два слоя, которые у нас лежат друг на друге:

- **прямоугольник** — контур самого устройства с чертежа (линии
  с `contur_color: "red"`);
- **кружок** — наш маркер: он несёт имя из контроллера, тип, артикул,
  описание и состояния, которых на чертеже нет.

Что можно сделать: ничего (у нас в окне так и выглядит); не рисовать красные
линии; попросить файл без них (`CONTUR_HMI_LINES=pipes`).

Если кружок стоит **ровно вправо-вниз на свой радиус** от символа — дело
в точке привязки: у нас `x, y` круга это центр, как в диалекте CONTUR (§5.2
вашей спецификации), и радиус вычитает ваш нормализатор. Если смещение
произвольное — скажите, это уже наша геометрия.

## 7. Что мы можем менять по просьбе

Переключается на нашей стороне, файл вы получаете готовым:

| Что | Значение | Зачем |
|---|---|---|
| `CONTUR_HMI_LINES` | `pipes` | без контуров устройств: чертёж вдвое легче |
| | `none` | вообще без чертежа |
| `CONTUR_HMI_FRAME` | `0` | без рамки и разлиновки штампа листа |
| `CONTUR_HMI_TEXTS` | `0` | без надписей чертежа |
| `CONTUR_HMI_GRID` | `0` | без привязки к сетке, точные координаты |
| `CONTUR_HMI_SCALE` | число | масштаб руками вместо расчётного |
| `CONTUR_HMI_STATES` | `0` | без `contur_states` |
| `CONTUR_HMI_STATE_COLORS` | `0` | состояния без `overrides` |
| `CONTUR_HMI_JUNCTIONS` | `0` | без точек сопряжения в `meta` |
| `CONTUR_HMI_META` | `0` | без элемента `meta` |
| `CONTUR_HMI_CONTOURS` | `0` | без рамок и имён техобъектов |
| `CONTUR_HMI_LABELS` | `0` | без подписей устройств |
| `CONTUR_HMI_GROUPS` | `1` | техобъект становится группой — см. §7.1 |

### 7.1 Режим групп (`CONTUR_HMI_GROUPS=1`)

- техобъект становится элементом `group` с `composition: true`;
- **первым ребёнком идёт рамка-`rectangle`** в локальных `(0, 0)` размером
  с группу: сама группа ничего не рисует, и без рамки её габарит схлопывается
  при первом же перетаскивании ребёнка;
- детьми становятся устройства, их подписи и имя техобъекта;
- **связь двусторонняя**: у ребёнка `parentKey`, у группы его ключ
  в `children`;
- **координаты детей локальные** и тоже кратны клетке; начало группы кратно
  клетке, поэтому локальная сетка совпадает с мировой.

Числа: A0 — 8466 элементов при 30 группах (у трёх контуров из 33 нет
сопоставленных устройств, их имена остаются верхнеуровневыми).

## 8. С чем сверяться при приёмке

Ваш список из §10 мы выполняем кодом при каждой сборке
(`python hmi_validate.py выгрузка.json`). Оба контрольных листа проходят его
без замечаний.

Контрольный лист A0 (`BN1-МОЛОКОХРАНИЛИЩЕ`, 3368×2384 пункта):

| Вид элемента | Сколько |
|---|---|
| `meta` | 1 |
| чертёж (`line`) | 7041 |
| надписи чертежа | 779 |
| рамки техобъектов (`rectangle`) | 33 |
| устройства (`circle`) | 233 |
| наши подписи и имена | 266 |
| **всего** | **8353** |

Холст после масштаба 4340×3060. Данные в тех же элементах: 1911 состояний
устройств, 64 программы операций, 767 трубопроводов, 250 связей, 4713 точек
сопряжения, 24 техобъекта.

## 9. Чего в этом файле нет

- **Разметки листа одной строкой** (наш SVG целиком). Она есть в XML
  и в `*.plant.json` полем `svg`; для холста бессмысленна — её содержимое
  и есть элементы этого файла.
- **Параметров техобъектов** (уставки, времена, `system_parameters`
  из `main.objects.lua`). В файле операции, состояния и шаги; уставки
  выгрузим, если нужны.
- **Сигналов ввода-вывода как отдельной сущности.** `DI`/`DO`/`AI`/`AO`
  попадают в файл только там, где нарисованы на листе, — обычными
  устройствами. Привязки «канал → модуль → узел» из `main.io.lua` не идут.
- **Коротких отрезков чертежа мы не убирали.** На A0 их 4039 из 7041: Eplan
  рисует символы короткими штрихами, а склейка коллинеарных (§9.1) дала
  около процента — склеивать почти нечего. Если они мешают, самый быстрый
  рычаг — `CONTUR_HMI_LINES=pipes`.

Второй наш формат, `*.plant.json`, по-прежнему существует: те же данные
деревом и разметка листа целиком. Он не для холста, а для потребителя,
которому нужен разбор, а не картинка.
