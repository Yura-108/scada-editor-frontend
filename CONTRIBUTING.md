# Работа с Git во фронтенде SCADA

Один законченный блок изменений проходит путь **ветка от `origin/dev` → локальные проверки → PR в `dev` → ревью → squash merge**. Это правило действует и для документации, настроек и небольших исправлений. `main` хранит стабильную версию. Выпуск в `main` оформляет ответственный за релиз отдельным PR. Прямые коммиты, прямой push, force push и удаление веток `dev` и `main` запрещены.

## Начало задачи

1. Проверьте рабочее дерево командой `git status --short --branch`. Сохраните чужие коммиты и незакоммиченные файлы на месте. Если в каталоге уже идёт другая задача, используйте отдельное рабочее дерево (`git worktree`).
2. Обновите сведения об удалённых ветках и создайте ветку **до первой правки**. Например, для исправления выбора тега:

   ```sh
   git fetch origin dev
   git switch --no-track -c fix/tag-picker-selection origin/dev
   ```

3. Назовите ветку по задаче, например `feat/scene-preview`, `fix/tag-picker-selection` или `docs/editor-guide`. Для веток Codex используйте `codex/<краткое-описание>`. Если продолжаете работу по открытому PR, используйте его ветку.
4. Меняйте файлы только в репозитории фронтенда. Соседний бэкенд доступен для чтения. Если нужно изменить его контракт, укажите зависимость в PR.

## Коммиты

- Собирайте в коммит одно осмысленное изменение. Перемещение файлов и изменение логики оформляйте разными коммитами. Добавляйте файлы явно и просматривайте `git diff --cached`.
- Используйте Conventional Commits для коммитов и заголовка PR. Например, `fix(editor): сохранять выбор слоя после переименования` или `docs: описать порядок ревью`. Область в скобках необязательна.
- После `npm ci` Husky подключает хук `pre-commit`. Он проверяет ветку и запускает `lint-staged` для подготовленных JS/TS/TSX. Исправляйте ошибки хуков. Обход через `--no-verify` и `HUSKY=0` запрещён.
- Проверьте, что в diff попали только файлы задачи. Локальные настройки, файлы с секретами, логи и артефакты сборки оставляйте вне коммита.

## Перед открытием PR

1. Из корня фронтенда выполните `npm run check:pr`. Команда последовательно запускает ESLint с нулевым допуском предупреждений, проверку типов, проверку циклов стора, проверку цветов интерфейса и production-сборку.
2. Запустите все настроенные в проекте наборы автотестов. Сейчас тестовый раннер отсутствует. При добавлении первого набора включите его в `check:pr` и обновите шаблон PR. При изменении поведения пройдите затронутый сценарий вручную и запишите результат.
3. Выполните `git fetch origin dev`, `git diff --check origin/dev...HEAD` и просмотрите `git diff origin/dev...HEAD`. Сверьте список коммитов через `git log --oneline origin/dev..HEAD`. Если возник конфликт с базой, влейте `origin/dev` в рабочую ветку, разрешите конфликт и повторите проверки на новом состоянии.
4. При сбое остановитесь до публикации PR, укажите команду и причину. После успешной проверки отправьте рабочую ветку (`git push -u origin HEAD`) и откройте PR с явной базой `dev`. GitHub по умолчанию может предложить `main`. Заполните [шаблон PR](.github/pull_request_template.md), приложите ссылку на задачу, если она есть, и скриншот при видимой правке интерфейса.

## Ревью и слияние

- Автор проверяет итоговый diff. Ответственный за фронтенд рассматривает PR и принимает решение о слиянии. Агент завершает блок ссылкой на открытый PR и результатами проверок. Самостоятельное слияние агентом требует явного поручения.
- Замечания исправляйте в той же ветке. После изменений повторите проверки на последнем коммите, обновите результаты в PR и закройте замечания с ревьюером. Дождитесь успешного завершения всех подключённых проверок GitHub.
- Для ветки задачи используйте **Squash and merge** в `dev`. Заголовок итогового коммита берите из PR. После слияния рабочую ветку можно удалить. Следующую задачу начинайте от обновлённой `origin/dev`.
