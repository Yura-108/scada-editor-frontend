# Работа с Git во фронтенде SCADA

Общие ветки находятся в **`savushkin-dev/scada-editor-frontend`**. Работа идёт через `dev`. Стабильная версия хранится в `main`, выпуск оформляется PR из `dev` в `main` с merge commit для сохранения истории. Прямые коммиты, прямой push, force push и удаление общих веток запрещены.

Один блок работы проходит путь **ветка от `upstream/dev` → проверки → PR в `savushkin-dev:dev` → ревью → squash merge**. Рабочую ветку можно опубликовать в своём форке.

## Начало задачи

1. Проверьте рабочее дерево командой `git status --short --branch`. Сохраните чужие коммиты и незакоммиченные файлы на месте. Если в каталоге уже идёт другая задача, используйте отдельное рабочее дерево (`git worktree`).
2. В клоне форка один раз добавьте `upstream`. Обновите `dev` и создайте ветку задачи **до первой правки**.

   ```sh
   git remote add upstream https://github.com/savushkin-dev/scada-editor-frontend.git
   git fetch upstream dev
   git switch --no-track -c fix/tag-picker-selection upstream/dev
   ```

3. Назовите ветку по задаче, например `feat/scene-preview`, `fix/tag-picker-selection` или `docs/editor-guide`. Для веток Codex используйте `codex/<краткое-описание>`. Если продолжаете работу по открытому PR, используйте его ветку.
4. Меняйте файлы только в репозитории фронтенда. Соседний бэкенд доступен для чтения. Если нужно изменить его контракт, укажите зависимость в PR.

## Коммиты

- Собирайте в коммит одно осмысленное изменение. Перемещение файлов и изменение логики оформляйте разными коммитами. Добавляйте файлы явно и просматривайте `git diff --cached`.
- Используйте Conventional Commits для коммитов и заголовка PR. Например, `fix(editor): сохранять выбор слоя после переименования` или `docs: описать порядок ревью`. Область в скобках необязательна.
- После `npm ci` Husky подключает хуки `pre-commit` и `commit-msg`. Первый проверяет ветку и запускает `lint-staged` для подготовленных JS/TS/TSX. Второй запускает Commitlint и отклоняет сообщения коммитов, которые нарушают правила Conventional Commits. Исправляйте ошибки хуков. Обход через `--no-verify` и `HUSKY=0` запрещён.
- Проверьте, что в diff попали только файлы задачи. Локальные настройки, файлы с секретами, логи и артефакты сборки оставляйте вне коммита.

## Перед открытием PR

1. Выполните `npm run check:pr`. Команда запускает ESLint без предупреждений, TypeScript, автотесты Vitest, проверки циклов стора и цветов и production-сборку. Для отдельного прогона тестов используйте `npm test`. Тесты BFF подставляют ответы gateway и работают без стенда.
2. При изменении поведения пройдите затронутый сценарий вручную и запишите результат.
3. Выполните `git fetch upstream dev`, `git diff --check upstream/dev...HEAD` и просмотрите `git diff upstream/dev...HEAD`. Сверьте список коммитов через `git log --oneline upstream/dev..HEAD`. При конфликте влейте `upstream/dev` в рабочую ветку, разрешите конфликт и повторите проверки.
4. При сбое остановитесь до публикации PR, укажите команду и причину. После успешной проверки отправьте рабочую ветку в форк (`git push -u origin HEAD`) и откройте PR с базой `savushkin-dev/scada-editor-frontend:dev`. Заполните [шаблон PR](.github/pull_request_template.md), приложите ссылку на задачу и скриншот при видимой правке интерфейса.

## Ревью и слияние

- Автор проверяет итоговый diff. Ответственный за фронтенд рассматривает PR и принимает решение о слиянии. Агент завершает блок ссылкой на открытый PR и результатами проверок. Самостоятельное слияние агентом требует явного поручения.
- Замечания исправляйте в той же ветке. После изменений повторите проверки на последнем коммите, обновите результаты в PR и закройте замечания с ревьюером. Дождитесь успешного завершения всех подключённых проверок GitHub.
- Для ветки задачи используйте **Squash and merge** в `dev`. Заголовок итогового коммита берите из PR. После слияния рабочую ветку можно удалить. Следующую задачу начинайте от обновлённой `upstream/dev`.

## Настройки CI и защиты веток

- Для `main` и `dev` исходного репозитория администратор включает слияние через PR, запрет force push и удаления и обязательные статусы GitHub Actions `Frontend checks`, `Docker build and smoke`, `Secret scan`, `PR title`. Добавляйте новые обязательные статусы после первого успешного прогона в репозитории.
- Gitleaks проверяет коммиты PR и обновлений общих веток. При первом push новой ветки проверяется её снимок. Значения находок скрываются в выводе.
- Dependabot открывает еженедельные PR обновлений npm и GitHub Actions в `dev`. Команда `npm audit --omit=dev --audit-level=high` проверяет production-зависимости в составе `Frontend checks`. Находки уровня `high` или `critical` и сбои аудита приводят к падению проверки. Перед PR с изменениями зависимостей запустите эту команду локально.
